Screen IDs are defined in the screen map; entity names are defined in the schema. Each final column is a proposed verification scenario, not an executed test.

## Coverage and acceptance boundary

All six flowchart sections, every named caller return, both gates, each distinct approval class, workbook sheets and major Part 1/Part 3 controls are represented above. Appendix drawings/fixture concepts are tracked as preliminary references, not manufactured acceptance rules. The matrix deliberately does not reconstruct missing original instruction text or missing source sheets.

Implementation verification should include each scenario above, negative authorization tests, all branch/return combinations and an end-to-end job dossier using controlled test data. This package has only been checked as design documentation; no application exists to execute these scenarios yet.

## Subsequent authority clarification

Self-approval is explicitly allowed initially. It grants no additional action/scope authority and waives no qualification, test, acceptance or evidence requirement. Verify that an unauthorized person remains unable to approve even their own work when self-approval is enabled. Add a versioned organization/action-scoped approval policy that the responsible authority may later restrict. For R30/R50/R51/R53, verify initial self-approval works, an effective restriction rejects the same performer/preparer as approver (including assisted/paper entry), and earlier approvals retain their historical policy. Personal owner exceptions remain attributable. These are proposed tests, not executed application checks.
